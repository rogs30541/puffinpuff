# v0.8.0 規劃：媒體通道抽象化（MediaHostProvider）— 開源商用版基礎

> 目標：把「讓 Meta 抓到媒體檔案」這件事抽象成可插拔的 Provider 架構，
> 讓開源商用版的使用者自行選擇並設定自有通道，同時根治 port 33344 佔用與 cloudflared 不穩問題。

---

## 1. 問題本質

### 為什麼需要「通道」？

| 平台 | 上傳方式 | 需要公開 URL？ |
|------|---------|---------------|
| YouTube | resumable upload（直接推檔案給 Google）| ❌ 不需要 |
| Facebook Reels | chunked upload（直接推檔案給 Meta）| ❌ 不需要 |
| FB Photo | `photos?url=` 或 multipart | 可用 multipart 直傳（現行已可）|
| **Instagram** | container API：`media?video_url=` / `image_url=` | ✅ **必須**（Meta 主動來抓）|
| **Threads** | container API：同 IG 模式 | ✅ **必須** |

→ **只有 IG / Threads 需要通道**。通道 = 讓一個本機檔案暫時有一個 Meta 抓得到的公開 HTTPS URL。

### 現行方案的痛點

| 方案 | 痛點 |
|------|------|
| Quick Tunnel（v0.1-0.4）| Cloudflare 對免帳號 tunnel 做 IP 限流（error 1015），高頻發布必撞 |
| Named Tunnel（v0.5+）| 固定 port 33344 → 高頻發布時 socket TIME_WAIT 佔用；cloudflared 進程每次 spawn/kill 開銷大、CLI 版本 bug 多（--no-autoupdate 事件）；需要使用者有 Cloudflare 帳號 + 自有網域 |

### 商用版額外需求
- 使用者不會人人有 Cloudflare 帳號/網域
- 不能把開發者自己的 credentials / 網域 bundle 進去
- 需要「零設定能動（低頻）」+「進階設定後穩定（高頻）」的分層體驗

## 2. 解法：MediaHostProvider 抽象 + 4 種實作

```ts
// src/main/lib/mediaHost/types.ts
export interface HostedMedia {
  /** Meta 可抓取的公開 HTTPS URL */
  url: string;
  /** 發布完成後呼叫：刪暫存物件 / 關 server / 關 tunnel */
  close(): Promise<void>;
}

export interface MediaHostProvider {
  readonly id: MediaHostProviderId;
  /** 把本機檔案變成公開可抓的 URL */
  host(args: {
    filePath: string;
    exposedName: string;
    onStatus?: (msg: string) => void;
  }): Promise<HostedMedia>;
  /** 設定頁「測試連線」用 */
  test(): Promise<{ ok: boolean; message: string }>;
}

export type MediaHostProviderId =
  | 's3-compatible'   // ⭐ 商用版推薦預設
  | 'named-tunnel'    // 既有，重構為 singleton
  | 'quick-tunnel'    // 既有，零設定 fallback
  | 'ngrok';          // 選配
```

### Provider A：`s3-compatible`（⭐ 新增，商用版主推）

**原理**：上傳檔案到使用者自己的 S3 相容儲存 → 產生公開（或 presigned）URL → Meta 來抓 → 發布完成後刪除物件。

**支援服務**（同一套 S3 API，只差 endpoint）：
| 服務 | 免費額度 | 出流量費 | 備註 |
|------|---------|---------|------|
| **Cloudflare R2**（推薦）| 10 GB 儲存/月 | **$0（零出流量費）** | 商用最划算 |
| AWS S3 | 12 個月 5GB | 有 | 企業用戶常有現成 |
| Backblaze B2 | 10 GB | 每日 3× 儲存量免費 | 便宜 |
| MinIO（自架）| 無限 | 自己頻寬 | 完全自主 |
| Supabase Storage | 1 GB | 2 GB/月 | 開發者熟 |

**使用者設定 4 欄**：
```
Endpoint URL     https://<accountid>.r2.cloudflarestorage.com
Bucket 名稱      puffinpuff-media
Access Key ID    ****
Secret Key       ****（DPAPI 加密存 DB）
公開 URL 前綴    https://pub-xxxx.r2.dev   （或自訂網域 / presigned 模式留空）
```

**優點**：
- ✅ 完全沒有本機 port → port 佔用問題根治
- ✅ 沒有 cloudflared 進程 → spawn/kill/CLI bug 全部消失
- ✅ 無限並發（同時發 10 支也各自獨立 URL）
- ✅ URL 穩定可靠，Meta 抓取成功率高（不經 tunnel 節點）
- ✅ AWS SDK v3 `@aws-sdk/client-s3` 一套通吃全部服務

**流程**：
```
upload PUT object (key: puffinpuff/<uuid>/<exposedName>)
  → URL = publicPrefix/<key>  （或 presigned GET, expires 1hr）
  → Meta container 抓取 → poll FINISHED → publish
  → close(): DeleteObject
```

### Provider B：`named-tunnel`（既有，重構 singleton）

保留給「不想用雲儲存、已有 Cloudflare」的使用者，但重構：

**現行問題**：每次上傳 spawn 一個 cloudflared + 開一個 server → 用完 kill → port TIME_WAIT。

**Singleton 重構**：
- App 啟動（或第一次需要時）只起 **一個** 常駐本機 server + **一個** 常駐 cloudflared 進程
- server 改為「多檔案註冊表」：`Map<exposedName, filePath>`，同時 serve 多個檔案
- 上傳時只是 `registry.set()` / 完成後 `registry.delete()`
- **port 永遠只 bind 一次** → 佔用問題根治
- cloudflared 不再反覆 spawn → 穩定性大增

### Provider C：`quick-tunnel`（既有，保留為零設定 fallback）

不動。新使用者第一次用、低頻場景還是最無痛。UI 標注「低頻用；高頻請設定物件儲存」。

### Provider D：`ngrok`（選配，P2）

有些使用者已有 ngrok 帳號。`ngrok http <port> --authtoken`。優先級低，可延後。

## 4. 開源商用版的另一塊：OAuth credentials 自帶

（本規劃聚焦通道；此節列待辦不展開）

現行 `secrets/*.json` bundle 開發者自己的 Google/Meta App → 商用版不可行。需要：
- 首次啟動 Setup Wizard：使用者貼自己的 Google OAuth client + Meta App credentials
- 文件：如何自建 Google Cloud 專案 / Meta App（一次性 30 分鐘設定）
- credentials 存 DB（DPAPI 加密），不再讀 secrets/ 檔案
- → 另立 v0.9.0 規劃

## 5. 實作階段

| 階段 | 內容 | 工程量 |
|------|------|--------|
| **Stage 1** | `MediaHostProvider` 介面 + 現行兩個 tunnel 包裝成 provider（行為不變）| 小 |
| **Stage 2** | `S3CompatibleProvider`（@aws-sdk/client-s3 + presigned + 刪除）| 中 |
| **Stage 3** | Named tunnel singleton 重構（常駐 server + 多檔案註冊表）| 中 |
| **Stage 4** | SettingsPage 新「媒體通道」卡片 + DB schema v11 + IPC | 中 |
| **Stage 5** | instagramAdapter / threadsAdapter 改呼叫 provider dispatcher | 小 |
| **Stage 6** | 測試（R2 實測）+ 打包 + CHANGELOG + README 通道設定教學 | 小 |

依賴新增：`@aws-sdk/client-s3`、`@aws-sdk/s3-request-presigner`（皆 Apache-2.0，可商用）。

## 6. 風險與備註

- R2 公開 bucket URL（r2.dev）有 rate limit，但遠高於個人發布需求；高量商用可綁自訂網域
- presigned URL 模式不需公開 bucket，更安全（URL 1 小時後自動失效）→ 預設用 presigned
- Meta 抓檔 timeout 約 60s，物件儲存的 TTFB 遠低於 tunnel，成功率只升不降
- 舊使用者升級：預設維持現行 provider 設定（quick/named），不強迫遷移
